# ADR-0057: 分析設計を直接結ばない論点は、下の論点の進捗を数で出す

## Status

Accepted

## Context

Epic 34（[#249](https://github.com/etoyama/insight-blueprint-skills/issues/249)、[DesignDoc](../design/epic-34-what-moved-the-answer.md)）の初版で決めた。
issue #249 の下調べで、主題のカードが「進捗: 未着手」と出ることが分かった。Epic 33 の後の epic ブランチ（dc785c4）でも同じだった。

比較の土台にした事実（`scripts/handoff_trial.py` の `build` に架空のシナリオを通し、HTML を読んだ。コードも読んだ）。

- 進捗は論点に直接結んだ分析設計の状態から導き、保存しない（`Progress.of`、`tree_render` の `_Context.of`）。下の論点は見ない。
- 主題の下の論点が3つ分析済みで、主題の答えを3回書いてあっても、主題のカードは「進捗: 未着手」と出る。「進捗の数」も主題を「未着手」に数える。
- 分析設計を `analyzing` のままにして、ツリーの決定で区切ると、論点のカードは「進捗: 検証中」「まだ答えていない」のままになる。区切った理由は「ツリーの決定」の一覧にだけ出る。
- 区切った論点は、ツリーの決定の `close` がその論点を指していることから導ける。

## Problem

- 課題1: 主題のカードの「未着手」を読んだ人は、何も進んでいないと読む。
- 課題2: 途中で止めた分析の論点は、止めたことと理由がカードから読めない。

扱わない範囲: 論点ごとの分析の状態を正本に持つこと（[#250](https://github.com/etoyama/insight-blueprint-skills/issues/250)）。「検証中」という言葉そのもの。

## Decision Analysis

|---|---|---|---|---|---|
| M1 | 進捗を保存しない | Must | - | - | [ADR-0024](0024-question-tree-yaml-and-generated-html.md)、`models/tree.py` |

- 案A: 分析設計を直接結ばない論点は、進捗の言葉を出さず、下の論点の進捗を数で出す。区切った論点のカードに理由を出す。
- 案B: 下の論点の分析設計をすべて集めて、1語にまとめる。
- 何もしない。

## Decision

案A を採る（人間の判断、2026-11-26）。決め手は W3 である。

この ADR はまだ `main` に入っていないので、1 から 3 は同じ日の試行の後に書き直した（下の「試行の後に直したこと」）。

1. 分析設計を自分には結ばず、下に置いた論点のどれかに結んでいる論点は、進捗の言葉を出さない。下のすべての論点の進捗を、言葉ごとの数で出す（「下の論点 4 つ: 分析済み 3、未着手 1」）。
2. 「進捗の数」は1 の論点を数えない。
3. 自分にも、下に置いた論点にも分析設計を結んでいない論点は「未着手」と出し、「進捗の数」にも数える。分析設計を直接結んだ論点は、今までどおり進捗の言葉を出す。どちらも、下に論点があれば、その数も添える。
4. その論点を指す最新のツリーの決定が「区切る」である論点は、カードに、区切った回と理由を出す。
5. 進捗（`Progress`）の3つの言葉の意味は変えない。どの値も保存しない。
6. 1 から 3 の規則は `QuestionTree.progress` の1か所に置く。ページ、`tree_io progress`、レポートは、どれもこれを呼ぶ。下の論点の数は `QuestionTree.progress_below` が数える。
7. `tree_io progress` は、論点ごとに `{"progress": 言葉か null, "below": {言葉: 数}}` を返す。`below` は分析済み・検証中・未着手の順で、数が0の言葉を出さない。キーは今までどおり論点の id である。skill は、`progress` が `null` の論点を、ページと同じ言い方（「この論点の下に置いた論点 N つ: …」）で伝え、未着手とは言わない。
8. レポートの論点の表の「進捗」の欄は、言葉のある論点は言葉を、言葉の無い論点はページと同じ下の論点の数（「この論点の下に置いた論点 N つ: …」）を出す。

### 試行の後に直したこと

最初の版の 1 は「分析設計を直接結んでいない論点で、下に論点があるもの」だった。この形には2つの穴があった。

- 規則がページにしか無かった。`tree_io progress` とレポートは、分析設計を結んでいない論点をすべて `not_started` と返した。図書館のシナリオでは、下の2つの論点が分析済みでも、主題が `not_started` になった。`/analysis-reflection` と `/analysis-framing` は、この値から「主題 Progress: 未着手」と分析者に出していた。この ADR が消そうとした表示である。
- 下の論点にも分析設計が無い論点（図書館の LIB-Q04。下に置いた LIB-Q06 にも分析設計が無い）が、言葉を失った。カードは「この論点の下に置いた論点 1 つ: 未着手 1」とだけ出し、「進捗の数」も数えなかった。同じページの「次の候補」と試行の鍵（`QuestionTree.untouched_nodes()`）は、LIB-Q04 を未着手として扱う。1つのページが2つの規則を持っていた。

表示を変えた後の試行（[記録](../handoff-trials/2026-11-26-after-the-display.md)）では、図書館の問い 2 で、sonnet・haiku・opus に3回ずつ読ませた 9 回のうち 6 回が、LIB-Q04 を未着手の論点から落とした。PM が今の 3 の規則の試作で同じ問いを 9 回読ませると、9 回とも正しかった。人間が PM のセッションで、この規則に直すと決めた（2026-11-26）。

## Consequences

### Positive

- 主題のカードが、下の論点がどこまで進んだかを数で伝える。
- ページ、`tree_io progress`、レポート、skill の伝え方が同じ規則に従う。規則が1か所にあるので、食い違わない。
- 「未着手」と「次の候補」が、同じ論点を指す。
- 止めた分析の理由が論点のカードで読める。

### Negative

- `tree_io progress` の値が、文字列から `progress` と `below` を持つオブジェクトに変わった。値を文字列として読んでいた呼び出し側は直す必要がある。リポジトリの中の呼び出し側（skill の手順とテスト）は直した。
- 区切った後に、同じ論点の下の論点だけを再開すると、カードの「区切った」が残る。その論点を指す新しい決定が出るまで消えない。
- 「検証中」は探索の分析でも出る。この決定では直さない。
- 区切った理由が引用を持つかは [ADR-0058](0058-a-tree-decision-may-cite-the-events-behind-its-reason.md) による。引用の無い理由は、文だけが出る。

## Alternatives considered

- **論点ごとの分析の状態を正本に持つ** — #250 の中身で、巡回の現在地の持ち方（[ADR-0026](0026-analysis-auto-walks-the-question-tree.md)）を変える。この Epic は表示と検査だけを扱う。
