# ADR-0051: 論点ツリーは分析設計を論点の下の枝に出し、状態を役割つきの言葉で言う

## Status

Accepted

## Context

Epic 32（[#217](https://github.com/etoyama/insight-blueprint-skills/issues/217)、[DesignDoc](../design/epic-32-exploration-and-confirmation.md)）の初版で決めた。
人間は論点と分析設計の記録を分けたまま、論点ツリーの表示で分析設計を論点の下に入れ子で出すと決めた（「論点ツリーの中に H 系がノードとして表示される形」）。
[ADR-0048](0048-intent-decides-the-form-and-the-end-of-a-design.md) は探索の終わりの状態 `explored` を足し、[ADR-0049](0049-legacy-exploration-stays-readable-and-is-marked.md) は旧形式の探索に印を付けると決めた。

比較の土台にした事実（main aec5a4c）。

- 今のページを合成シナリオで出して読んだ（`python -m scripts.handoff_trial build --scenario lib`）。論点のカードは「根拠を開く」の中の「結んだ分析設計」に「LIB-H02 … 状態: inconclusive」と出す。開かないと分析設計は見えない。
- 分析ノートとレポートは、結論の冒頭に同じ定型文（`LEAD_SENTENCES`。「仮説は支持された。」など）を使う（`skills/_shared/design_note.py`、`skills/_shared/theme_report.py`）。
- 分析ノートは証拠を「仮説を支持する証拠」「仮説に反する証拠」「向きの無い証拠」に分ける。論点ツリーは引用した出来事に「direction: supports（仮説を支持する）」と添える。
- レポートの分析設計の表は「仮説」の列を持つ。
- 表示は正本から決定的に生成し、モデルに書かせない（[ADR-0024](0024-question-tree-yaml-and-generated-html.md)、PRD の非機能要件）。
- 見本を Artifact に作り、人間が2つの切り替え（入れ子の形、状態の言葉）を見比べた。見本はコミットしていない。

## Problem

- 課題1: 分析設計が「根拠を開く」の中にあり、開くと「状態: rejected」が論点の属性に見える。読み手は論点が却下されたと読む。
- 課題2: 検証仮説の判定と、論点への現時点の答えは別のものである。合成シナリオの見本では、1つの論点に判定が「支持」と「棄却」の2つ並び、論点の答えは「未判別」だった。同じ「状態」の語で出すと混ざる。
- 課題3: 分析ノートとレポートの定型文が、探索にも「仮説は支持された。」と出る。

扱わない範囲: 派生の節（分析設計の親子）は残す。ページの配色。現時点の答えの書き方。

## Decision Analysis

形式は `decision-analysis` スキルに従う（[FLOW-0004](flow/0004-decision-analysis-plugin.md)）。案ごとの見本を見比べてもらってから聞いた（[FLOW-0009](flow/0009-designdoc-decisions-scope-first.md)）。

| # | 基準 | 区分 | 分類 | 重み（決めた人） | 出典 |
|---|---|---|---|---|---|
| M1 | 分析設計が、論点の下に入れ子で出る | Must | - | - | 人間の決定（表示で入れ子にする） |
| M2 | 表示の文は、記録から決定的に作る | Must | - | - | PRD の非機能要件、ADR-0024 |
| W1 | 判定が論点のものではなく分析設計のものだと、開かずに読める | Want | 解決 | 高（人間。「H 系がノードとして表示される形」） | 課題1、課題2 |
| W2 | 探索に判定の言葉が出ない | Want | 解決 | 高（人間。Epic 32 の範囲の決定） | 課題3 |
| W3 | ページの縦の長さ | Want | 費用 | 低（Claude の推測） | 引き継ぎの試行（読み手が現在地を探す） |

### 入れ子の形

| Must | N1. 論点の下の枝に、分析設計のカードを出す | N2. 論点のカードの中に、分析設計の行を出す | 何もしない |
|---|---|---|---|
| M1 | 満たす | 満たす | 満たさない（「根拠を開く」の中） |
| M2 | 満たす | 満たす | 満たす |

| Want | N1 | N2 |
|---|---|---|
| W1 | 枝として見える。論点と分析設計が形で分かれ、探索の問いと検証仮説の文も出る | 論点のカードの中に判定が入るので、論点の属性に見えやすい |
| W3 | 分析設計1つにつき、カード1枚ぶん伸びる | 短い |

### 状態の言葉

| Must | S1. 役割つきの日本語 | S2. 英語の値のまま |
|---|---|---|
| M2 | 満たす（状態と形から決まる） | 満たす |

| Want | S1 | S2 |
|---|---|---|
| W1 | 「検証仮説の判定」と名乗るので、誰の判定かが文で分かる | 「状態: rejected」が論点の近くに出る |
| W2 | 探索に判定の語が出ない | `explored` は判定に見えないが、検証と同じ「状態」の語で出る |

### 探索の結論の冒頭の定型文

| 候補 | 評価 |
|---|---|
| 探索を終えた。判定はしていない。 | `explored` の意味（答えが出たかは言わない）と合う |
| 探索の問いに測って答えた。判定はしていない。 | 測れなかった探索にも出るので、嘘になることがある |
| 探索済み。 | 短いが、判定が無い理由が読み手に伝わらない |

- 差がつく基準: 入れ子の形は W1 と W3、状態の言葉は W1。
- 感度: W3 を高にする（分析設計が1つの論点に何本も付くテーマが多い）なら N2 に変わる。

| 案 | 起きうる悪い結果 | 抑え方 |
|---|---|---|
| N1 | 分析設計が複数の論点に結ばれると、同じカードが複数の枝に出る | 2つ目の論点からは短い行にする |
| N2 | 判定が論点のカードの中に戻る | 帯の見出しで分ける |
| S1 | 日本語の語と YAML の値の対応を、分析者が覚える必要がある | 凡例に対応表を出す |
| S2 | 元の読み違えが残る | なし |
| 何もしない | 論点が却下されたように読める表示が残る | なし |

## Decision

N1 と S1 を採る。人間が見本を見比べて選んだ（2026-11-25、Epic 32 の DesignDoc 初版のセッションで直接）。決め手は W1。

1. 論点ツリーの HTML は論点に結んだ分析設計を、その論点の下の枝に出す。枝のカードは論点のカードと形を変え、id、題、意図、探索の問いか検証仮説、状態の言葉、分析ノートへのリンクを持つ。子の論点より先に並べる。
2. 複数の論点に結んだ分析設計は、2つ目の論点からは、id・状態の言葉・最初に出た論点へのリンクだけの短い行にする。
3. 状態の言葉を次のとおりにする。凡例に YAML の値との対応を出す。

   | 形と状態 | 表示の言葉 |
   |---|---|
   | `in_review` | レビュー中 |
   | `revision_requested` | 修正待ち |
   | `analyzing` | 分析中 |
   | 探索の `explored` | 探索済み（判定はしない） |
   | 検証の `supported` / `rejected` / `inconclusive` | 検証仮説の判定: 支持 / 棄却 / 結論できず |
   | 旧形式の探索の `supported` / `rejected` / `inconclusive` | 仮説の判定: 支持 / 棄却 / 結論できず |

4. 意図の言葉は、探索、検証、探索（旧形式）、探索と検証（旧形式）の4つである。
5. 論点のカードには答えの文の上に「現時点の答え」の見出しを出す。
6. 分析ノートとレポートの定型文を、形で分ける。

   | 場所 | 探索 | 検証 | 旧形式の探索 |
   |---|---|---|---|
   | 分析ノートの冒頭の節 | 探索の問いと背景 | 検証仮説と背景 | 仮説と背景 |
   | 証拠の群 | 証拠（1群） | 検証仮説を支持する証拠 / 検証仮説に反する証拠 | 仮説を支持する証拠 / 仮説に反する証拠 |
   | 結論の冒頭 | 探索を終えた。判定はしていない。 | 検証仮説は支持された。/ 検証仮説は棄却された。/ 検証仮説を支持するとも棄却するとも結論できなかった。 | 仮説は支持された。/ 仮説は棄却された。/ 仮説を支持するとも棄却するとも結論できなかった。 |
   | 論点ツリーの引用の向き | 出さない | 検証仮説を支持する / 検証仮説に反する | 仮説を支持する / 仮説に反する |
   | レポートの分析設計の表 | 意図の列を足し、「仮説」の列を「探索の問い / 検証仮説」にする | 同じ | 意図は「探索（旧形式）」 |

7. 言葉と定型文は1か所に置き、論点ツリー・分析ノート・レポートが同じものを読む。

## Consequences

### Positive

- 分析設計が開かなくても論点の下に見える。判定は分析設計のカードの中にあり、「検証仮説の判定」と名乗る。
- 探索には、どの面でも判定の言葉が出ない。
- 分析ノートとレポートは、同じ定型文を出し続ける。

### Negative

- ページが縦に伸びる。分析設計の多い論点では、子の論点が下に押される。
- 表示の言葉と YAML の値が一致しなくなる。凡例で補う。
- 論点ツリーの表示が変わるので、引き継ぎの試行の正解の鍵と合成シナリオを直す。直した後の表示で、試行はまだ回していない。
- 見本で確かめていない点が3つある。複数の論点に結んだ分析設計の短い行、凡例の対応表、派生の節との重なりである。Story 32.6 で実物を出して確かめる。

## Alternatives considered

- **分析設計を論点と同じ見た目の枝にする** — 論点（問い）と分析設計が形で分かれず、元の取り違えに近づく。見本を作る前に落とした。
