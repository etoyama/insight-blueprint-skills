# ADR-0048: 分析の意図が、分析設計の形と終わり方を決める

## Status

Accepted

## Context

Epic 32（[#217](https://github.com/etoyama/insight-blueprint-skills/issues/217)、[DesignDoc](../design/epic-32-exploration-and-confirmation.md)）の初版で決めた。

e-Stat の実データ試行（テーマ FRN）で、人間が論点（Q 系）と分析設計の仮説（H 系）を取り違えた。
FRN の3件の分析設計はすべて `exploratory` だが、どれも仮説の文を持ち、`supported` / `rejected` / `inconclusive` が付いた。
FRN-H01 は開いた問い（どれだけ違うか）を測る分析なのに、「振れ幅 1.5」という閾値を作って判定している（issue の記載）。

人間は次の設計思想を決めた（2026-11-25）。論点はいつも問いである。仮説は問いに先に置く仮の答えで、検証のときだけ置く。
探索は測って答え、判定しない。検証は基準を先に固定して判定する。探索の分析設計には仮説にあたるものも見込みも置かない。
検証の分析設計が持つ仮説の呼び名は造語にし、別の意味が浸透した既存の語（作業仮説）は避ける。

比較の土台にした事実（main aec5a4c。ファイルを読み、`grep` で確かめた）。

- `AnalysisDesign.hypothesis_statement` と `hypothesis_background` は必須の `str` である（`src/insight_blueprint/models/design.py`）。
- 意図で分岐する Python のコードは無い。`mixed` の分岐は notebook の契約にも無い。
- `create_design` と model の `analysis_intent` の既定は `confirmatory` である。
- `validate_transition(current, target)` は意図を受け取らない。呼ぶのは `skills/_shared/design_io.py` の2か所だけである。
- terminal status の集合を使う7か所は、集合に入っているかだけを見る。`skills/premortem/lib/risk_evaluator.py` は自前の写しを持つ。
- 分析設計は論点への参照を持たない。論点ツリーの無いテーマでも分析設計は作れる。1つの分析設計を複数の論点に結べる。
- `next_action` は `if_supported` / `if_rejected` の形で、判定を前提にする。
- 分析設計の id（`{theme}-H{nn}`）は、journal の出来事の id、論点の `design_ids`・発見元・引用、notebook・verdict・図・lineage のファイル名に埋まっている。`src/insight_blueprint/models/tree.py` は `{theme}-H\d+` で検査する。hook は `_hypothesis.yaml` で終わるファイルを検査の対象にする。
- 用語集の「問い」を含む語は4つある（論点、根の問い、未解決の問い、journal の出来事の `question`）。journal の `hypothesize` は「仮説」と訳されている。
- model の形は公開の契約ではない。守るのは、保存済みの YAML が読めることと、plugin の中の呼び出し側だけである（[ADR-0047](0047-stop-publishing-to-pypi.md)）。

## Problem

- 課題1: 分析者が開いた問いを測る探索でも仮説を書かされ、終わりに判定を付けさせられる。放置すると、作り物の閾値と判定が記録に残り続ける。
- 課題2: 探索が仮説を持たなくなると、その記録が何に答える分析かを言う項目が無くなる。論点の問いは広く、分析設計が測るものは狭い。論点ツリーの無いテーマでは、借りる論点も無い。
- 課題3: `mixed` は、探索の問いと検証仮説のどちらを持つのか、終わりに判定するのかが決まらない。
- 課題4: 結果を見た後に探索を検証へ書き換えられると、基準を先に固定して判定することが破れる。
- 課題5: 用語集の「仮説」は分析設計の項目を指す。探索の途中の見込み（journal の `hypothesize`）と同じ語で呼ぶと、2つが混ざる。素の「問い」は既に4つの語が使っている。

扱わない範囲: 今ある探索の記録の読み方（[ADR-0049](0049-legacy-exploration-stays-readable-and-is-marked.md)）、notebook の契約（[ADR-0050](0050-exploration-keeps-values-and-confirmation-fixes-its-criterion.md)）、表示の言葉（[ADR-0051](0051-designs-nest-under-their-question-and-state-is-worded-by-role.md)）。

## Decision Analysis

形式は `decision-analysis` スキルに従う（[FLOW-0004](flow/0004-decision-analysis-plugin.md)）。5つの判断を、依存の順に人間に聞いた。基準は判断ごとに立てたので、判断ごとに表を置く。

### 起きうる悪い結果

| 案 | 起きうる悪い結果 | 抑え方 |
|---|---|---|
| 探索は自前の問いを持つ | 論点の問いをそのまま写した分析設計が増え、二重管理になる | design の入口で、論点より狭く、測るものが分かる問いを書かせる。review の観点に入れる |
| 論点の問いを借りる | ツリーの無いテーマで、何を測ったかが後から読めない | 題に問いを書く規約（機械では確かめられない） |
| 検証仮説と探索の問い | 会話で「仮説」「問い」と略され、元の混同に戻る | 用語集の「使わない言い換え」に、分析設計の項目を指す素の「仮説」「問い」を入れる |
| 項目を足すだけ | `hypothesis_*` という名前が、探索の記録に空で残って見える | 探索では項目ごと書かない（空文字も置かない） |
| 改名する | 別名の読み替えに穴があり、古い YAML が読めなくなる | 保存済みの形のテスト |
| `mixed` は新しく作れない | 眺めた後に1つ検定する分析が、2つの分析設計になる | reflection が派生で2つ目を作る道を案内する |
| `mixed` を残す | 探索なのに判定する形が、`mixed` の名で残る | なし |
| 意図は分析の前だけ変えられる | `analyzing` に入った直後に気づいたまちがいが直せない | `in_review` に戻せば直せる |
| `explored` を1つ足す | 何も言えなかった探索も同じ状態になり、一覧で見分けられない | 論点の現時点の答えの種類（未判別）で見分ける。ツリーの無いテーマでは結論の文を読む |
| id を変えない | id だけが出る場面で、探索を仮説と読む | 一覧に意図を出す |
| 新しい記号にする | 1つのテーマに2つの記号が混ざる。2つの形を読む道に穴が出ると、記録が読めなくなる | 保存済みの形のテスト |
| 何もしない | 次の実データ試行で同じ取り違えが起きる | なし |

## Decision

分析の意図が分析設計の形と終わり方を決める。どれも人間が選んだ（2026-11-25、Epic 32 の DesignDoc 初版のセッションで直接）。

1. 探索の分析設計は探索の問い（`exploration_question`）とその背景（`exploration_background`）を必ず持つ。検証仮説・その背景・`next_action` を持てない。決め手は、論点ツリーの無いテーマでも何に答えるかが読めること。
2. 検証の分析設計は検証仮説（`hypothesis_statement`）とその背景（`hypothesis_background`）を必ず持つ。探索の問いとその背景を持てない。問いの文は持たず、問いは結んだ論点にある。
3. 用語を次のとおりにする。検証の分析設計が持つ仮説を「検証仮説」、探索の分析設計が持つ問いを「探索の問い」と呼ぶ。素の「仮説」は問いに先に置く仮の答えを指し、journal の `hypothesize` が記録する。コード上の名前は改名せず、探索の2項目を足す。
4. `mixed` は新しく作れない。保存済みの `mixed` は読め、検証として扱う。model の既定の値は `confirmatory` のままにし、入口は必ず意図を聞いて明示して書く。
5. 意図を変えられるのは、状態が `in_review` か `revision_requested` の間だけにする。`analyzing` より後は変えられず、別の意図の分析は派生で作る。例外は旧形式の探索を `confirmatory` に直すことである（[ADR-0049](0049-legacy-exploration-stays-readable-and-is-marked.md)）。
6. terminal status に `explored` を足す。探索の分析設計が結論で進める状態は `explored` だけで、検証は `explored` へ進めない。答えが出たかどうかは、状態ではなく、結論の文と論点の現時点の答えが持つ。`premortem` は自前の集合をやめ、正本の `TERMINAL_STATUSES` を使う。
7. 分析設計の id の記号 `H` とファイル名の `_hypothesis.yaml` は変えない。`H` は分析設計の通し番号の記号だと用語集に書く。
8. 分析設計の形（探索、検証、旧形式の探索）は、意図と項目から導き、保存しない（`DesignForm`）。検査・遷移・表示は形を見て分ける。

## Consequences

### Positive

- 開いた問いを測る分析に、作り物の仮説と判定が付かなくなる。
- 検証仮説は結果を見る前に書いたものだけになる。
- 保存済みの YAML は手を入れずに読める。id もファイル名も変わらない。
- 意図による分岐が形という1つの値に集まる。

### Negative

- 1つの集約に、意図で排他な項目の組が2つできる。検査が形の決まりを持つ。
- 探索の中で1つだけ検定したい分析は、2つの分析設計になる。
- id の `H` は探索の分析設計にも付く。用語集の定義と表示で補うが、id だけが出る場面では仮説に見える。
- 何も言えなかった探索と、答えの出た探索が、同じ `explored` になる。
- 論点の問いを写しただけの探索の問いを、機械では止められない。review の観点で拾う。

## Alternatives considered

- **事前仮説** — 事前登録の文脈で使われる語で、別の意味が浸透している。
- **探索に、仮説の代わりに見込みの項目を持たせる** — 人間が先に退けた（設計思想の3）。残すなら journal に書く。
- **論点と分析設計の記録を1つにまとめる** — 人間が先に退けた（設計思想の1）。記録は分け、表示で入れ子にする。
