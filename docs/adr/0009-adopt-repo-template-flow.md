# ADR-0009: repo-template の開発フローを採用する

## Status

Accepted

## Context

このリポジトリの開発フロー（Epic / Story / DesignDoc / ADR）は、CLAUDE.md と `.claude/rules/` の
テンプレート2本で定義してきた。同じ作者がこのフローを
[etoyama/repo-template](https://github.com/etoyama/repo-template) に切り出して改訂した。
改訂後のフローは要求と背景の正本を DesignDoc に置き、用語の正本を1ファイルに持ち、
ADR に Problem と Decision Analysis の節を足している。このリポジトリは改訂前の形のままで、
フローの定義が2つのリポジトリで食い違っていた。

2026-11-15 に、このリポジトリを repo-template のフローに合わせると人間が決めた。
採用するコミットは `921b1bcdac979bd285e539a9578025a5c1a39bc0` に固定する。
ブランチモデル（[ADR-0002](0002-trunk-based-epic-stacking.md)）と ADR のハードルール（CLAUDE.md §5）は、
すでに repo-template と一致しているので変えない。

比較の前提にした事実は次のとおり。確かめた方法を括弧に書く。

- repo-template は自分の ADR を `docs/adr/0001`〜`0004` に持つ。このリポジトリにも
  ADR-0001〜0004 があり、番号が衝突する（両方の `docs/adr/` を `ls` した）。
- このリポジトリの ADR-0001〜0004 は、`src/`・`hooks/`・`skills/`・`tests/`・CI・CHANGELOG を含む
  64行から参照されている（`main` の `8d1523e` で `git grep -nE 'ADR-000[1-4]|adr/000[1-4]'` を実行した）。
- repo-template の中で `docs/adr/` の外から自分の ADR を参照する箇所は、10ファイル・16行ある
  （`921b1bc` で同じ `grep` を実行した）。どの置き方を選んでも、コピーするファイルではここを書き換える。
- 既存の DesignDoc は13本・1,764行、ADR は8本・621行ある（`wc -l` で数えた）。
- skill から `docs/adr/0005`・`0006`・`0008` と `docs/design/epic-10-analysis-report.md` へ、
  パスで参照する箇所が5つある（`git grep -nE 'docs/(adr|design)/' -- skills` を実行した）。
- repo-template の FLOW-0004 は「既存の ADR は書き直さない。新しい ADR から適用する」としている
  （[flow/0004](flow/0004-decision-analysis-plugin.md) の Decision を読んだ）。
- 既存の DesignDoc 13本はすべて冒頭に背景の文を持ち、Test Design Matrix に未完了はなく、
  Epic issue はすべて closed である（判断時の調査による。この ADR を書くときには確かめ直していない）。
- 直近の merged PR 20本（Dependabot を除く）は、Epic が10本、単発の chore / fix / feat が10本だった
  （判断時の調査による。同上）。

## Problem

- 課題1: repo-template の ADR をそのままコピーすると、「ADR-0001」が2つの決定を指す。
  読む人も AI もどちらの決定か文脈から推測することになる。
- 課題2: コピーしないと、WORKFLOW とテンプレートが決定の出典として張っているリンクが切れる。
- 課題3: repo-template が進むたびに読み替える箇所が多いと、更新を取り込まなくなる。
- 課題4: 新旧の形式が混在する。旧形式の文書は21本あり、次に書く人や AI が手本にしうる。
- 課題5: 旧形式の文書を後から新形式に書き直すと、当時なかった材料が当時の記録として残る。
- 課題6: 機械的なコピーと判断を含む書き換えを1本の PR に混ぜると、レビューで精査しきれない。
- 課題7: 新しいフローで Epic を起票するための道具（起票フォーム、label、テンプレート）を入れるのが、
  この作業自体である。道具が `main` に入るまで、新しいフローでは起票できない。

扱わない範囲: CLAUDE.md の再編、PRD と ARCHITECTURE の更新、ユビキタス言語の中身、
skill の TDD の解釈、Domain Model の全体図の置き場。これらは準拠の Epic で扱い、
必要なものは別の ADR に書く。

## Decision Analysis

決めることは3つある。repo-template の ADR の置き方（D1）、既存文書の扱い（D2・D3）、進め方（D10）。
重みを「Claude の推測」としたものは、人間が案を選んだ時点で追認している。

### D1: repo-template の ADR の置き方

| # | 基準 | 区分 | 分類 | 重み（決めた人） | 出典 |
|---|---|---|---|---|---|
| M1 | 「ADR-NNNN」が1つの決定だけを指す | Must | - | - | 課題1 |
| M2 | コピーした文書の ADR リンクが切れない | Must | - | - | 課題2 |
| W1 | repo-template の更新時の読み替えが少ない | Want | 解決 | 高（Claude の推測） | 課題3 |
| W2 | フローの根拠をリポジトリ内で読める | Want | 解決 | 中（Claude の推測） | 課題2 |
| W3 | ADR の採番と索引の運用が単純 | Want | 費用 | 中（Claude の推測） | adr-template |

| Must | 何もしない（0001〜0004 のままコピー） | A. 0009〜0012 に採番し直す | B. `docs/adr/flow/` に番号を保って置く | C. コピーせず URL で参照 |
|---|---|---|---|---|
| M1 | 満たさない（同じ番号が2つの決定を指す） | 満たす | 満たす（表記を `FLOW-000N` にする） | 満たす |
| M2 | 満たす | 満たす | 満たす | 満たす（リンク先を URL に変える） |

| Want | A. 採番し直す | B. `flow/` に置く | C. URL で参照 |
|---|---|---|---|
| W1 | 番号とファイル名が変わる。更新のたびに対応表を引いて読み替える | 変わるのは接頭辞とディレクトリだけで、置換で済む | 本文をコピーしないので、ADR の読み替えはない。リンクの書き換えは残る |
| W2 | 読める | 読める | 読めない。根拠は外のリポジトリにあり、固定したコミットを開く必要がある |

- 差がつく基準: A は W1 で、C は W2 で、B は W3 で劣る。決め手は W1。
- 感度: repo-template の更新をほぼ取り込まないなら A、根拠が外にあってよいなら C に変わる。

| 案 | 起きうる悪い結果 | 抑え方 |
|---|---|---|
| A | 更新を取り込むたびに番号の対応を間違え、別の決定を参照する | 対応表を置く |
| B | フローの決定が `docs/adr/` と `flow/` の2か所に散る | `flow/` にはコピーだけを置き、このリポジトリの決定はすべて `docs/adr/` に置く |
| C | repo-template の文書が動くと、根拠を読めなくなる | URL をコミットで固定する |

|---|---|---|---|

| 案 | 起きうる悪い結果 | 抑え方 |

| C | 1本目と2本目の間、WORKFLOW と CLAUDE.md が食い違う | CLAUDE.md §4 に「WORKFLOW を正とする」と書き、Epic を間を置かずに始める |

## Decision

repo-template の `921b1bcdac979bd285e539a9578025a5c1a39bc0` の開発フローを採用する。
これより新しいコミットは別の決定なしには取り込まない。

- **D1**: B を採る。決め手は W1。
  - repo-template の ADR 0001〜0004 を、番号とファイル名を保って `docs/adr/flow/` に置く。
  - 表記は `FLOW-000N` とする。`ADR-000N` は、このリポジトリの `docs/adr/` の決定だけを指す。
  - `flow/` には repo-template のコピーだけを置く。このリポジトリで行った決定は、
    フローに関するものも含めて `docs/adr/` に置く。
- **D2・D3**: A を採る。決め手は W1 と W3。
  - Epic 10 までの DesignDoc 13本と ADR-0001〜0008 は、旧形式のまま変えない。
  - 新形式はこの ADR-0009 と、準拠の Epic の DesignDoc から使う。
  - 閉じた Epic の DesignDoc には追記しない。機能を直すときは、新しい Epic を新形式で切る。
  - 事実の誤りは、人間が確かめたうえで直してよい。
- **D10**: C を採る。決め手は W1 と W3。
  - 1本目は chore PR で、repo-template のファイルの移植とこの ADR だけを含む。
  - 2本目は新しいフローで起票する Epic で、判断を含む変更を扱う。
  - 1本目で、CLAUDE.md §4 に「フローの定義の正本は `docs/WORKFLOW.md`」の1行を足す。

## Consequences

### Positive

- フローの定義が repo-template と揃い、更新を取り込むときの差分が接頭辞とディレクトリだけになる。
- WORKFLOW とテンプレートが参照する決定を、リポジトリの中で読める。
- どの文書から新形式かがこの ADR と `docs/adr/README.md` の索引で分かる。
- Epic を起票する時点で、起票フォームと新しいテンプレートが `main` にある。

### Negative

- ADR の系統が2つになる。`FLOW-000N` と `ADR-000N` を取り違えると、別の決定を参照する。
- `FLOW-` の接頭辞と `flow/` という置き場所は、repo-template が想定していない形である。
  repo-template の側で派生リポジトリへの取り込み方を決めたら、ここも決め直す。
- 旧形式の文書が21本残る。過去の Epic の背景は、冒頭の背景文より詳しくは辿れない。
- `flow/` の本文は repo-template のままなので、「CLAUDE.md の `## 8. Language`」のように、
  このリポジトリの構成と合わない記述が残る。
- 準拠の Epic が終わるまで、CLAUDE.md は旧フローの記述を持ち続ける。
  CLAUDE.md §11 が指す rules のうち、3本は存在しないままである。
- `type:story` の label は、マージ後に人間が `scripts/bootstrap.sh` を実行するまで存在しない。
- プラグインの宣言と検証 hook が同じ `.claude/settings.json` で共存するかは、
  `scripts/install-plugins.sh` を実行するまで確かめられていない。

## Alternatives considered

- **このリポジトリの ADR-0001〜0004 を採番し直す** — 64行の参照と、公開済みの CHANGELOG を書き換えることになる。
