# ADR-0062: 論点ツリーと分析設計は対話エージェントだけが書き、読んでから書くまでをロックする

## Status

Accepted

## Context

Epic 35（[#284](https://github.com/etoyama/insight-blueprint-skills/issues/284)、[DesignDoc](../design/epic-35-hand-over-questions.md)）の初版で決めた。
互いを待たない論点をまとめて任せると、複数の分析が同じセッションの中で並行で走る。
本書は分析者と話す `/analysis-auto` のセッションの Claude を対話エージェント、分析設計を1つ渡されて実行するサブエージェントを実行エージェントと呼ぶ（人間が選んだ、2026-11-27）。

比較の土台にした事実（main 9d26c39、図書館の合成シナリオ、2プロセス同時、各20回）。

- `design_io.create_design` を同時に呼ぶと、20回中20回、同じ id になり、片方が黙って上書きされた。`next_design_id` は読んでから書くまでロックしない。
- `tree_io.link_design` を同時に呼ぶと、20回中20回、片方の結び付けが消えた。`answer`・`decide`・`add_node` も同じ形である。
- 今のロックは書き戻す一瞬だけに掛かる（`skills/_shared/_atomic.py` の `atomic_write_yaml`）。
- 読んでから書くまでを `filelock` のロックで囲むと、同じ id は20回中0回、消えた結び付けは20回中0回、エラーは0回だった。`filelock` は既に依存にある。
- 実データで手で通したとき、対話エージェントが論点ツリーと分析設計を順に書き、実行エージェントが自分の notebook と journal だけを書く分け方では、ぶつからなかった（1回）。
- `/analysis-notebook` の Step 7 は `tree_io render` で論点ツリーの HTML を書き直す。実行エージェントの1人は指示に反してこれを走らせた。
- journal は分析設計ごとの別ファイルである。
- 確かめていないこと: ロックを待つ時間が実際の分析で気になるか。

## Problem

- 課題1: 2つの実行エージェントが同時に分析設計を作ると、片方が黙って上書きされる。
- 課題2: 同時に論点ツリーを書くと、片方の書き込みが消える。
- 課題3: 複数の実行エージェントが同じ論点ツリーの HTML を書くと、ほかの分析の結果が抜けた HTML が残りうる。

扱わない範囲: セッションをまたぐ実行。別のワークツリーで同じ id が別の分析設計を指すこと。

## Decision Analysis

| # | 基準 | 区分 | 分類 | 重み（決めた人） | 出典 |
|---|---|---|---|---|---|
| M1 | 並行で呼ばれても、記録が黙って消えない | Must | - | - | 課題1、課題2 |
| W1 | 実行エージェントが指示を外しても壊れない | Want | 解決 | 高（Claude の推測） | 課題3、[ADR-0005](0005-selective-autonomous-chaining.md) の Negative |
| W2 | 分析者が読む HTML が、古い内容で上書きされない | Want | 解決 | 中（Claude の推測） | 課題3 |
| W3 | 変える所が少ない | Want | 費用 | 中（Claude の推測） | YAGNI |

- 案A: 分担とロックの両方。対話エージェントだけが論点ツリー・分析設計・論点ツリーの HTML を書き、実行エージェントは自分の notebook・verdict・journal だけを書く。加えて、読んでから書くまでをロックする。
- 案B: 分担だけ。
- 案C: ロックだけ。実行エージェントも論点ツリーと HTML を書いてよい。
- 何もしない。

| Must | 案A | 案B | 案C | 何もしない |
|---|---|---|---|---|
| M1 | 満たす | 満たさない。分担は skill の文で、外れると消える | 満たす | 満たさない |

| Want | 案A | 案C |
|---|---|---|
| W1 | 指示を外しても、ロックが記録を守る | 記録は守る |
| W2 | 対話エージェントが書くので、全部の結果が入った HTML になる | 先に読んだ古い状態で後から書くと、ほかの分析の結果が抜けた HTML が残りうる |
| W3 | ロックの helper 1つと、それを使う書き込みの関数。skill 2本の文 | ロックだけ |

- 差がつく基準: W2 だけである。
- 感度: W3 を高にしても、案C は W2 が残るので変わらない。

| 案 | 起きうる悪い結果 | 抑え方 |
|---|---|---|
| 案A | 実行エージェントが落ちて、ロックのファイルが残る | `filelock` は OS のロックで、プロセスが終われば外れる |
| 案A | `/analysis-notebook` を単独で起動したとき、HTML が更新されなくなる | 単独の起動では今までどおり Step 7 を走らせる |
| 案B | 記録が黙って消える | 無い |
| 案C | 抜けた HTML を分析者が読む | 抑えにくい |
| 何もしない | 課題1〜3 が残る | 無い |

## Decision

案A を採る（人間の判断、2026-11-27）。決め手は M1 と W2 である。

1. まとめて任せた実行では、論点ツリーの YAML、分析設計、論点ツリーの HTML を書くのは対話エージェントだけである。対話エージェントの書き込みは順に行う。
2. 実行エージェントが書くのは、渡された分析設計の notebook・verdict・journal だけである。
3. まとめて任せた実行では、実行エージェントは `/analysis-notebook` の Step 7 の `tree_io render` を走らせない。対話エージェントが、実行エージェントの戻りのたびに書き直す。単独で起動した `/analysis-notebook` は、今までどおり自分で書き直す。
4. `design_io` と `tree_io` の書き込みは読んでから書き戻すまでを1つのロックで囲む。分析設計の id の採番から書き込みまで、分析設計の更新と状態の遷移、journal の追記、論点ツリーを書く命令の全部が対象である。ロックの helper は `skills/_shared/_atomic.py` に1つ置く。
5. 文書と skill は2つの役目を対話エージェント、実行エージェントと呼ぶ。

## Consequences

### Positive

- 並行で呼ばれても、分析設計の id は重ならず、論点ツリーの書き込みは消えない。
- 分析者が開く HTML は、対話エージェントが最後に書いた、全部の結果が入ったものになる。
- ロックは単独の起動にも効く。2つのセッションが同じ `.insight/` を書いても、同じ守りが効く。

### Negative

- 分担は skill の文で、守るかは実行エージェントに頼る。外れたときに記録を守るのはロックで、HTML の古さは守れない。対話エージェントが後から書き直すので、最後には正しくなる。
- 論点ツリーの HTML の書き直しは原子的だが、読んでから書くまでのロックは掛けない。HTML は正本から作り直せる。
- ロックは同じファイルシステムの上でだけ効く。

## Alternatives considered

- **実行エージェントごとに別のワークツリーで走らせ、後で合流する** — 分析設計の id はワークツリーの中でだけ一意で、合流のときに重なる。データの置き場所も写す必要がある。
