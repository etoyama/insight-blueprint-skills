# ADR-0038: DesignDoc 初版では、全体の整合を確かめ、成果物の見本を見せてから承認を求める

## Status

Accepted

## Context

[docs/WORKFLOW.md](../WORKFLOW.md) §4 は、DesignDoc 初版で埋める節と、初版を出す前の確認を1つだけ決めている。
「この DesignDoc だけを読んだ人が、誰のどんな課題を解くのか説明できるか」である。
判断を1件ずつ聞いた後に全体を見直すことと、利用者が触る成果物を承認の前に見せることは決めていない。

Epic 28（[#173](https://github.com/etoyama/insight-blueprint-skills/issues/173)）の DesignDoc 初版のセッションは、
決めること7件を Decision Analysis の形式で1件ずつ聞いた後、この2つを自分の判断で行った（2026-11-22）。

- **全体の整合**: 7件がそろった後、全体を見渡して確かめた。判断2（手元の HTML だけを入口にするか）が見直され、
  ほかに3点（経過の節を分ける、図を埋め込む、生のファイルは手元のリンクにする）が決まった
  （段取りボードの判断の行と、issue #173 のコメントで確かめた）。
- **見本**: 初版の後、論点ツリー・分析ノート・レポートの見本を Artifact に出した。
  人間がスマホのアプリで開いて確かめると、Artifact の中で通るのは同じページの中のアンカーだけだった。
  別の HTML へのリンク、新しいタブ、枠での埋め込み、script での読み込みは通らなかった。
  これで、初版の ADR-0037 が前提にしていた「分析ノートを添えるファイルとして送る」が成り立たないと分かった。
  DesignDoc が「未確認」として Story の最初に回していた確認が、初版の承認の前に済んだ。

人間はこの2つを「とても良かった。標準のプロセスにしたい」と評価した（このリポジトリの親セッション、2026-11-22）。

## Problem

- 課題1: 判断を1件ずつ聞くと、それぞれは筋が通っていても、組み合わせると矛盾することがある。
  見直さないまま Story に入ると、実装の途中で判断を戻すことになる。
- 課題2: DesignDoc の文と図だけでは、人間は利用者が触る成果物の姿を思い描きにくい。
  ホストの制約のような前提も、文書の上では「未確認」のまま残る。外れていると分かるのは Story に入った後になり、
  ADR と Story の分割を作り直すことになる。

扱わない範囲: 見本の作り方そのもの（どの道具で、どこまで作り込むか）。Story の実装中の確認。

## Decision Analysis

| # | 基準 | 区分 | 分類 | 重み（決めた人） | 出典 |
|---|---|---|---|---|---|
| M1 | 判断の組み合わせの矛盾を、Story に入る前に見つけられる | Must | - | - | 課題1 |
| M2 | 成果物の姿と前提を、初版の承認の前に人間が確かめられる | Must | - | - | 課題2、人間の発言 |
| W1 | どのセッションでも、毎回同じように行われる | Want | 解決 | 高（人間） | 人間の発言（「標準のプロセスにしたい」） |
| W2 | 初版の手間が増えすぎない | Want | 費用 | 中（Claude の推測） | - |

| Must | 何もしない | A. WORKFLOW §4 の初版の手順に2つを足す | B. メモリにだけ残す |
|---|---|---|---|
| M1 | 満たさない（セッションの判断に任される） | 満たす | 満たす |
| M2 | 満たさない | 満たす | 満たす |

| Want | A. WORKFLOW §4 に足す | B. メモリにだけ残す |
|---|---|---|
| W1 | 正本に書くので、どのセッションも、ほかの貢献者も読む。構造テストで消えないようにできる | 親セッションのブリーフに頼る。ブリーフを書かずに始めたセッションには届かない |
| W2 | 見本を作る手間が増える。成果物を持たない Epic では見本を作らずに済む | 同じ |

- 差がつく基準: W1。
- 感度: 利用者が触る成果物を持たない Epic ばかりなら、見本の段は形だけになる。そのときは見本の段を任意にする。

| 案 | 起きうる悪い結果 | 抑え方 |
|---|---|---|
| A | 見本を作り込みすぎ、初版が遅れる | 見本はコミットせず使い捨てにする。確かめたいことに絞る |
| A | 見本がそのまま実装の仕様として扱われる | 見本で分かった事実は DesignDoc か ADR に書き戻し、正本はそちらに置く |

## Decision

A を採る。決め手は W1。
DesignDoc 初版では、人間の承認を求める前に、全体の整合の確認と、利用者が触る成果物の見本による擦り合わせを行う。
手順の正本は [docs/WORKFLOW.md](../WORKFLOW.md) §4 に置き、
[.claude/rules/design-doc-template.md](../../.claude/rules/design-doc-template.md) からそこを指す。

## Consequences

### Positive

- 判断の矛盾とホストの制約が、Story の分割の前に見つかる。
- 人間は文書でなく成果物の姿で初版を判断できる。

### Negative

- 初版の手間が増える。見本を作る分、承認までの往復も増えうる。
- 見本で確かめられるのは、見本で再現できた範囲だけである。Epic 28 でも、スマホのアプリで確かめた結果で、
  デスクトップのブラウザでは確かめていない。

## Alternatives considered

- **上流の repo-template の決定を待つ** — 上流には issue を立てた（etoyama/repo-template）。
  採られるまで待つと、次の Epic の初版に間に合わない。採られたら [flow/](flow/README.md) のコピーを更新し、この ADR を置き換える。
