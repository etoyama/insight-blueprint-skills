# FLOW-0005: DesignDoc 初版では、全体の整合を確かめ、成果物の見本を見せてから承認を求める

## Status

Accepted

## Context

[docs/WORKFLOW.md](../WORKFLOW.md) §4 は、DesignDoc 初版で埋める節と、初版を出す前の確認を1つだけ決めていた。
「この DesignDoc だけを読んだ人が、誰のどんな課題を解くのか説明できるか」である。
判断を1件ずつ聞いた後で全体を見直すことと、利用者が触る成果物の姿を承認の前に見せることは、
決めていなかった。

このテンプレートの派生先で、ある Epic の DesignDoc 初版を書いた AI が、この2つを自分の判断で行った。
例として、そのとき起きたことを書く（etoyama/insight-blueprint-skills の Epic 28、2026-11-22）。

- **全体の整合**: 決めること7件を Decision Analysis の形式（[FLOW-0004](0004-decision-analysis-plugin.md)）で
  1件ずつ聞き、そろった後で全体を見渡した。すでに決めた判断の1つが見直され、ほかに3点が新しく決まった。
  1件ずつ聞くだけでは、組み合わせたときの矛盾が残っていた。
- **見本**: 初版の後、利用者が触る HTML の見本を、その HTML が実際に届く場所（Claude の Artifact）に出した。
  人間が開いて確かめると、Artifact の中で通るのは同じページの中のアンカーだけで、別の HTML へのリンクは開けなかった。
  初版の ADR が前提にしていた届け方は成り立たないと分かった。DesignDoc が「未確認」として
  最初の Story に回していた確認が、初版の承認の前に済んだ。

人間はこの2つを評価し、標準のプロセスにしたいと言った。派生先では先に自前の ADR として取り入れ、
上流のこの repo に提案した（[#3](https://github.com/etoyama/repo-template/issues/3)）。

比べるときに前提にした事実は次のとおり。

- 前提の崩れが見つかったのは、成果物が実際に届く場所に見本を置いたからである。
  手元の HTML で同じ見本を開いていたら、アンカーの制約は出なかった（派生先の ADR の Context を読んで確かめた）。
- Artifact は Claude のアプリの機能である。CLI だけの環境やほかの AI ツールでは使えない。
  このテンプレートは配布先を選ばない。
- 黙って判断して先へ進むことは禁止している（[CLAUDE.md](../../CLAUDE.md) §5）。
- DesignDoc の Story Timeline は、Story の完了とキーイベントを追記するだけのログで、
  初版のときの出来事も書ける（[design-doc-template](../../.claude/rules/design-doc-template.md) を読んで確かめた）。

## Problem

- 課題1: 判断を1件ずつ聞くと、それぞれは筋が通っていても、組み合わせると矛盾することがある。
  見直さないまま Story に入ると、実装の途中で判断を戻すことになる。
- 課題2: DesignDoc の文と図だけでは、人間は利用者が触る成果物の姿を思い描きにくい。
  ホストの制約のような前提も、文書の上では「未確認」のまま残る。外れていると Story に入ってから分かると、
  ADR と Story の分割を作り直すことになる。

扱わない範囲: 見本の作り方（どの道具で作り、どこまで作り込むか）。Story の実装中の確認。

### 見本を省けるとき

- 課題3: 内部のリファクタリングのように、利用者から見える変化がない Epic でも見本を必須にすると、
  形だけの見本を作る手間がかかるか、守られない決まりが1つ増える。
- 課題4: 省いてよいとすると、見本が効く Epic でも、AI が「成果物がない」と見なして黙って飛ばしうる。

## Decision

A を採る。決め手は W1。手順の正本は [docs/WORKFLOW.md](../WORKFLOW.md) §4 に置き、
[.claude/rules/design-doc-template.md](../../.claude/rules/design-doc-template.md) からそこを指す。

DesignDoc 初版では、人間の承認を求める前に次の2段を行う。

1. **全体の整合**: 個別の判断がそろったら、全体を見渡して確かめる。判断どうしが矛盾していないか、
   AC・Scope・既存の ADR とかみ合うかを見る。直す点があれば、人間に示して決め直す。
2. **見本**: 利用者が触る成果物（画面、HTML、レポート、CLI の出力、API、生成されるファイルなど）の見本を作り、
   人間とイメージを合わせる。
   - 置き場は問わない。成果物が実際に届く場所があれば、そこに置き、そのホストの制約も確かめる。
     届く場所がなければ、人間が開ける場所でよい。
   - 見本はコミットしない。見本で分かった事実と、確かめていない前提を、DesignDoc か ADR に書き戻す。
   - 利用者から見える変化がない Epic では省いてよい。省いたら、その理由を Story Timeline に1行書く。

## Consequences

### Positive

- 判断どうしの矛盾とホストの制約が、Story の分割の前に見つかる。
- 人間は文書だけでなく成果物の姿を見て初版を判断できる。
- 見本を省いた Epic にも跡が残り、レビューで差し戻せる。

### Negative

- 初版の手間が増える。見本を作る分、承認までの往復も増えうる。
- 見本で確かめられるのは、見本で再現できた範囲だけである。届く場所が複数あるとき（スマホとデスクトップなど）、
  そのすべてで確かめるとは決めていない。
- 「利用者から見える変化がない」の見極めは AI に任せる。もっともらしい理由で省かれることは、レビューでしか止められない。
- 2段を行ったかどうかを機械的に検査する仕組みは入れていない。

## Alternatives considered

- **全体の整合を Decision Analysis の形式に足す** — 形式の正本は decision-analysis プラグインにあり（FLOW-0004）、
  1件の判断の提示を扱う。複数の判断を見渡す手順は DesignDoc の初版の手順なので、WORKFLOW に置く。
