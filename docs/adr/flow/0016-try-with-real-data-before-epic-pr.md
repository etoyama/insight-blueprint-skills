# FLOW-0016: 利用者が触る Epic では、ゲートの後、Epic PR の前に、実データで使ってみる

## Status

Accepted

## Context

[docs/WORKFLOW.md §4](../../WORKFLOW.md) の Epic 完了は、Test Design Matrix 全✓ をゲートにする。
PM セッションのスキル `.claude/skills/pm-session/SKILL.md` の §7 は、ゲートで全体のレビュー（バグ・セキュリティとコード品質）と推敲を回し、
直してから Epic PR を開く。利用者が実際の場所で使ってみる段は無い。
DesignDoc 初版の「見本」の段（[FLOW-0005](0005-designdoc-draft-checks-whole-and-mockup.md)）は、作る前にイメージを合わせる段で、作った後の確かめではない。

このテンプレートの派生先の Epic 32（etoyama/insight-blueprint-skills、[#217](https://github.com/etoyama/insight-blueprint-skills/issues/217)、2026-11-25）で、
次のことが起きた。振り返り（#217 のコメント）と、試したセッションが共有ノートに残した findings で確かめた。

- ゲートのレビューと直しの後、人間の依頼で、実際の分析のリポジトリで epic ブランチの plugin を使った（11:17–14:49）。
- findings は、試したセッションが1件1節で共有ノートに残した（F01〜F21）。人間が仕分け、3件を Epic で直し、5件を issue にした。
- 次の3件は構造テストにもゲートのレビューにも見つからず、実データの会話で見つかった。
  - F20: reflection がレビューを `conclude` の後に勧めるので、レビューを受けると `conclude` が2つになる。
  - F05: Framing Brief 無しで作った分析設計が、論点に結ばれない。
  - F12: 最初の答えが短くても、skill がそのまま探索の結論として受け取る。
- 試す準備で2回やり直した（plugin の入れ方と、入ったことの確かめ方）。

## Problem

- 課題1: 利用者の会話の流れや実データでだけ出る穴が、Epic PR とリリースの後まで残る。
- 課題2: 試す段が人間の思いつきに任されると、Epic ごとに行ったり行わなかったりする。準備の手順も毎回作り直す。
- 課題3: 利用者から見える変化の無い Epic にも課すと、手間だけが増える。

扱わない範囲: 試す場所を用意する具体的な手順（成果物の種類ごとに違うので、各リポジトリに置く）。

## Decision Analysis

| # | 基準 | 区分 | 分類 | 重み（決めた人） | 出典 |
|---|---|---|---|---|---|
| M1 | 利用者が触る Epic では、Epic PR の前に、実際の場所で使う機会がある | Must | - | - | 課題1 |
| W1 | Epic ごとにぶれず、準備を作り直さない | Want | 解決 | 高（人間。束 B を採った） | 課題2 |
| W2 | 変化の無い Epic に手間を課さない | Want | 費用 | 中（Claude の推測） | 課題3 |
| W3 | Epic PR とリリースが遅れない | Want | 費用 | 中（Claude の推測） | - |

| Must | A. ゲートの後、Epic PR の前に置く。変化の無い Epic では理由を書いて省く | B. Epic PR を開いた後、マージの前に置く | C. リリースの後、振り返りの前に置く | 何もしない（人間が頼んだときだけ） |
|---|---|---|---|---|
| M1 | 満たす | 満たす | 満たさない（リリースの後になる） | 満たさない（頼まれないと無い） |

| Want | A | B |
|---|---|---|
| W1 | フローの段なので毎回行う。省くときは理由が残る | 段としては同じ。ただし、直しが PR のレビューの途中に積まれる |
| W2 | 見本の段と同じく、理由を1行書けば省ける | 同じ |
| W3 | Epic 32 では3時間半かかった。Epic PR がその分遅れる | PR は早く開くが、マージは同じだけ遅れる |

- 差がつく基準: W1。
- 感度: レビューの途中に直しが積まれることを気にしないなら、B でも結論は変わらない。W3 を高くすると、どちらも何もしないに負ける。

| 案 | 起きうる悪い結果 | 抑え方 |
|---|---|---|
| A | findings が多く、Epic PR がいつまでも開かない | 人間が「Epic で直す / issue にする」に仕分ける。Epic で直すのは人間が選んだものだけ |
| A | 試す場所の設定を戻し忘れ、利用者の環境に epic ブランチの版が残る | 準備と元に戻す手順を、始める前に共有ノートに書く |
| A | 試す場所で、epic ブランチの版ではなく、入っている版が読まれている | 一覧ではなく、実際に呼んで確かめる |
| A | 「変化が無い」を理由に、触る Epic でも省かれる | 省いた理由を Story Timeline に書き、Epic PR のレビューで人間が見る |

## Decision

A を採る。定義の正本は WORKFLOW §4 の5、PM の回し方の正本は pm-session §7 に置く。

- 利用者が触る Epic では、ゲートのレビューと直しの後、Epic PR を開く前に、利用者が実際に使う場所で、epic ブランチの成果物を実データで使う。
- findings は、人間が「Epic で直す / issue にする」に仕分ける。
- 利用者から見える変化の無い Epic では省いてよい。省いたら、その理由を Story Timeline に1行書く（初版の「見本」の段と同じ扱い）。

人間が束 B として採った（派生先の Epic 32 の振り返り、2026-11-25）。決め手は M1 と W1。

## Consequences

### Positive

- 構造テストとレビューで見つからない穴を、Epic PR とリリースの前に拾える。
- 直すか先送りかを人間が決めるので、Epic の範囲が膨らまない。

### Negative

- Epic PR が遅れる。Epic 32 では準備のやり直しを含めて3時間半かかった。
- 試す場所を用意する手順は、成果物の種類ごとに各リポジトリで書く必要がある。テンプレートには置かない。
- 根拠は1件（Epic 32）だけである。

## Alternatives considered

- **Story ごとに実データで使う** — Story は動作確認できる最小単位だが、利用者の会話の流れは Story をまたぐ。Story ごとに試す場所を用意する手間も、Story の数だけ増える。
