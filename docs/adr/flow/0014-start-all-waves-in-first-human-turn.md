# FLOW-0014: 後に続く波の子は、最初に子を立てる人間のターンで、全部待機の指示で立てておく

## Status

Accepted

## Context

PM セッション（[FLOW-0006](0006-pm-session-and-board.md)）のスキル `.claude/skills/pm-session/SKILL.md` は、
子の完了通知で始まったターンでは `start_session` が拒まれ、`SendMessage` は通ることを前提に、子を前もって立てる。
[FLOW-0011](0011-start-wave-one-before-designdoc-approval.md) は波 1 の子を DesignDoc 初版の子を立てるターンで立てると決めた。
波 2 から後は扱わない範囲とし、§5 の「波を始めるターンで、その波の後に続く Story も立てる」のままにした。

このテンプレートの派生先の Epic 32（etoyama/insight-blueprint-skills、[#217](https://github.com/etoyama/insight-blueprint-skills/issues/217)、2026-11-25）で、
次のことが起きた。振り返り（#217 のコメント）とボードのログで確かめた。

- 起票の後、人間の一言で W1 を立て、そのターンで W2 を待機で立てた（09:21–09:49）。
- W2 の本題は W1 の子の完了通知のターンで送った。W2 を始めたターンは人間のターンではなかったので、W3 を立てられなかった。
- W3 を立てるのに、人間の伝言が1回要った（10:13–10:17）。

§5 の「波を始めるターン」は、人間のターンであることを前提にしている。FLOW-0011 の後は、波 1 から後のどの波も完了通知のターンで始まるので、この前提は成り立たない。

## Problem

- 課題1: 波が3つ以上ある Epic では、波ごとに人間の伝言が要る。FLOW-0006 と FLOW-0011 が減らそうとした中継が残る。
- 課題2: 前もって立てる子が増えると、分割が変わったときに余る子と、モデルを決める前に立てる子も増える。

扱わない範囲: 分割そのものの決め方。アプリが同時に持てるセッションの数の上限。

## Decision Analysis

| # | 基準 | 区分 | 分類 | 重み（決めた人） | 出典 |
|---|---|---|---|---|---|
| W1 | 波が何本あっても、波の移りに人間の手が要らない | Want | 解決 | 高（人間。束 A を採った） | 課題1 |
| W2 | 使わない子と手順の増加が少ない | Want | 費用 | 中（Claude の推測） | 課題2 |

Must に当たる基準は無い（どの案も課題を程度で解く）。

| Want | A. 最初に子を立てる人間のターンで、全部の波の子を待機で立てる | B. 人間のターンが来るたびに、次の波まで立てる（今の §5） | 何もしない |
|---|---|---|---|
| W1 | 仮の分割の本数が合えば、人間の手は要らない。足りなければ次の人間のターンで立てる | 波の移りが完了通知のターンなので、波 3 から後は毎回一言要る | 同じ |
| W2 | 待機の子が Story の数だけ並ぶ。分割が外れると余る。モデルは仮の分割で決める | 待機の子は1波分だけ | 増えない |

- 差がつく基準: W1 と W2。
- 感度: W2 を高くすれば B に変わる。W1 の重みは人間が決めた。

| 案 | 起きうる悪い結果 | 抑え方 |
|---|---|---|
| A | 待機の子が、初版より前の epic ブランチから切られる | 本題の最初に `git fetch origin && git merge --ff-only origin/<epic ブランチ>` を書く（§5 の既存の手順） |
| A | 分割が変わり、子が足りない・余る | 足りない分は次の人間のターンで立てる。待てなければ `waiting_human` にして一言で頼む。余りは本題を送らないと決まったターンでアーカイブする |
| A | アプリが同時に立てられるセッションの数に上限があり、途中で拒まれる | 拒まれた分のボードの行を `waiting_human` にして、§5 の「起動できないターン」の手順に回す |
| A | 最初の人間のターンが Remote Control から来て、`start_session` が拒まれる | 同じく「起動できないターン」の手順に回す |
| 何もしない | 波が3つ以上ある Epic で、人間の伝言が波ごとに要る | なし |

## Decision

A を採る。手順の正本は `.claude/skills/pm-session/SKILL.md` の §1、§3、§5 に置く。

- 最初に子を立てる人間のターン（DesignDoc 初版の子を立てるターン）で、仮の分割の全部の波の子を、待機の指示で立てる。
- 名前は FLOW-0011 の形を波の番号に広げ、`<Epic の issue>-w<波>-<n>` にする。
- 本題は、波 1 には起票の後の完了通知のターンで、後の波には前の波が終わった完了通知のターンで、`SendMessage` で送る。
- 本数が足りなければ次の人間のターンで立てる。余った子はアーカイブする。

この決定は FLOW-0011 を波 2 から後に広げる。FLOW-0011 は置き換えない。

人間が束 A として採った（派生先の Epic 32 の振り返り、2026-11-25）。決め手は W1。

## Consequences

### Positive

- 分割が仮の形のとおりなら、設計の段から最後の波まで、人間の伝言が要らない。
- 「波を始めるターン」が人間のターンかどうかを、PM が見分けなくてよくなる。

### Negative

- 待機の子が Story の数だけ並ぶ。サイドバーが混み、分割が外れたときの片付けが増える。
- 後の波の子ほど、立ててから本題まで長く待つ。その間に epic ブランチが進むので、取り込みが必須になる。
- アプリのセッション数の上限は確かめていない。
- 根拠は1件（Epic 32）だけである。

## Alternatives considered

- **人間に、波が移るたびに「次を立てて」と送ってもらう決まりにする** — 振り返りで減らしたいとされた中継そのものを、手順として固定することになる。
