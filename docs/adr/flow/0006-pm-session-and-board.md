# FLOW-0006: Epic は PM セッションが段取りボードで統括し、作業は子セッションに渡す

## Status

Accepted

## Context

[docs/WORKFLOW.md](../WORKFLOW.md) は、Epic・Story・DesignDoc・ADR の流れを決めている。
Claude Code のセッションをどう分け、人間がどこで判断と承認をするかは決めていない。

このテンプレートの派生先（etoyama/insight-blueprint-skills）は、Epic 18 と Epic 28 で次の運用を試した。
Epic 28（2026-11-22〜23）の記録で、その運用を確かめた。

- 1つの親セッション（PM セッション、opus）が、Epic の段取りを Artifact の db で持つページ（段取りボード）に置いた。
- DesignDoc 初版、Story 6本、単発の作業2本を、子セッションに渡した。子のモデルは、未決の判断の量で fable・opus・sonnet から選んだ。
- 人間は、ボードの「あなたの番」と、各子セッションで聞かれた判断にだけ答えた。

確かめた事実は次のとおり（ボードのログ 44 件、PR、issue、コミットを読んで確かめた）。

- 13:58 にボードを立ててから、翌 05:51 に v0.15.0 を出すまでに、子セッションを 10 本立てた。並行で走らせたのは、Story の2組（28.2 と 28.4、28.3 と 28.5）と単発の2本である。同じファイルを取り合うことは無かった。事前に決めた3つが効いた。触るファイルの重なりで波を組むこと、ADR の番号を範囲で振ること、引き継ぎを共有ノートで渡すことである。
- epic ブランチのコミットは 48 本で、仕様変更が3本、fix が7本だった。途中でモデルを上げ直した Story は無かった。
- 人間の手が機械的な往復に挟まった所が5〜7回あった（「〜を立てて」の送り直しが5回、子の間の中継が1回、「私のボールは何か」の問い合わせが1回）。どれも運用の手順で防げた。
- 人間はこの運用を「非常に良い。今後の開発のデファクトにしたい。repo-template にも還元したい」と評価した。

運用の手順は、派生先のメモリにしか無かった。

## Problem

- 課題1: セッションの分け方と人間の判断の場所が決まっていないと、人間が進み具合を追うために各セッションを渡り歩くことになる。
- 課題2: 運用の手順が派生先のメモリにしか無いと、新しいリポジトリや別の人には届かない。
- 課題3: 手順の抜けで、人間の手が機械的な往復に挟まった（起動できないターン、人間待ちの子への伝言、ボードの抽出の誤り）。

扱わない範囲: 開発フローそのもの（WORKFLOW のまま）。Story の完了の条件（FLOW-0007）。人間に聞く判断の条件（FLOW-0008）。

## Decision Analysis

| # | 基準 | 区分 | 分類 | 重み（決めた人） | 出典 |
|---|---|---|---|---|---|
| M1 | 人間が判断と承認の行き先を1か所で見られる | Must | - | - | 課題1 |
| M2 | 手順の正本が1か所 | Must | - | - | WORKFLOW §2 |
| W1 | テンプレートの配布先にも届く | Want | 解決 | 高（人間） | 課題2、人間の発言 |
| W2 | 機械的な往復が減る | Want | 解決 | 高（人間） | 課題3 |
| W3 | Claude Code の desktop アプリが無い環境での扱い | Want | 費用 | 中（Claude の推測） | - |

| Must | A. PM のスキルを `.claude/skills/pm-session/` に置く | B. WORKFLOW に手順を書く | 何もしない |
|---|---|---|---|
| M1 | 満たす | 満たす | 満たさない |
| M2 | 満たす | 満たす | 満たす（派生先のメモリだけ） |

| Want | A. スキル | B. WORKFLOW |
|---|---|---|
| W1 | 届く。ボードのページの雛形も一緒に配れる | 届く。雛形は別に置くことになる |
| W2 | 起動できないターンの扱いなど、道具に依存する手順まで書ける | 道具に依存する手順が、道具を選ばない開発フローに混ざる |
| W3 | スキルが前提を書き、無い環境では WORKFLOW のとおり1つのセッションで進めると書ける | WORKFLOW が desktop アプリを前提にすることになる |

- 差がつく基準: W2 と W3。
- 感度: どの重みを動かしても変わらない。

| 案 | 起きうる悪い結果 | 抑え方 |
|---|---|---|
| A | ツールの仕様が変わり、スキルの手順が古くなる | 気づいた所で、スキルの文を直す PR を出す |
| B | 開発フローに道具の手順が混ざり、読みにくくなる | なし |
| 何もしない | 配布先で同じ詰まりを繰り返す | なし |

## Decision

A を採る。Epic は PM セッションが段取りボードで統括し、作業は子セッションに渡す。
手順の正本は `.claude/skills/pm-session/SKILL.md` に置き、ボードのページの雛形を同じフォルダの `board.html` に置く。
決め手は W2 と W3 で、道具に依存する手順を開発フローから分けておける。

## Consequences

### Positive

- 人間は、ボードの「あなたの番」と、子セッションで聞かれた判断にだけ答えればよい。
- 並行の作業の取り合いを、波と番号の範囲と共有ノートで防げる。

### Negative

- Claude Code の desktop アプリの道具（`start_session`・`detach_session`・Artifact の db）に依存する。無い環境では使えない。
- 子の完了通知のターンからは子を起動できない。人間の一言が残る（スキルの5に書いた）。

## Alternatives considered

- **ボードを GitHub の Projects にする** — 子セッションが状態を更新する経路が増え、人間待ちの行に何をすればよいか（`action`）を書く場所も無い。
