# ADR-0071: 食い違いは読む前に見せて聞き、結果のレビューは解釈と交絡に絞る

## Status

Accepted

## Context

Epic 36（[#302](https://github.com/etoyama/insight-blueprint-skills/issues/302)、[DesignDoc](../design/epic-36-before-the-analyst-answers.md)）の初版で決めた。
[ADR-0070](0070-the-computation-is-checked-against-the-design-before-the-analyst-reads.md) は、計算の点検を分析者が読む前に済ませると決めた。
この ADR は点検で食い違いが出たときの扱いと、点検と重なる結果のレビューの観点を決める。

比較の土台にした事実（v0.22.0 を読んだ）。

- まとめて任せる流れでは、戻った分析の終え方を、1つの問いにまとめて聞く
  （Epic 35 の Decision `story-35-7-the-endings-are-asked-in-one-question`）。分析設計ごとに、`/analysis-reflection` の Step 3 の3つの問いを並べる。
- `design_io stop` は結果が記録にある分析を止めない（[ADR-0064](0064-a-handed-over-analysis-asks-before-changing-what-was-read-and-can-be-stopped.md) の 7）。
  食い違いがある分析に「止める」は選べない。
- 実行エージェントは、任せる前に分析者が読んだ内容を変えないと進めないとき、データに触る前に止まって聞く（ADR-0064）。
  それでも、Epic 35 の実データで使う段では、設計に無い比べ先を足した分析が、聞かずに戻った。
- 結果のレビュー（`skills/analysis-review/SKILL.md` の Step 3b）の5つの観点のうち、判定の線の写しと cell の並びは、
  notebook が分析設計と契約のとおりかを見る観点で、計算の点検の項目と重なる。
- `/analysis-reflection` の Step 4 の目安は、探索でもレビューを勧める場面を2つ挙げる。分析が設計に無いものを足したときと、
  数の照合がデータの中の足し上げだけのときである。前者は計算の点検が拾う。

## Problem

- 課題1: 食い違いが出たとき、何を自動で行い、何を分析者に聞くかが決まっていない。
- 課題2: 結果のレビューの観点が計算の点検と重なる。同じ指摘が2か所に出る。
- 課題3: 結果のレビューは、分析者が言う「解釈と交絡の批評」を観点に持たない。

扱わない範囲: 計算し直した分析の journal に残る、前の実行の出来事の扱い。

## Decision Analysis

決めることは2つある。食い違いの扱い（判断1）と、結果のレビューの観点（判断2）である。

| # | 基準 | 区分 | 分類 | 重み（決めた人） | 出典 |
|---|---|---|---|---|---|
| M1 | 分析者が読んだ内容に関わる変更を、聞かずに行わない | Must | - | - | ADR-0064 |
| W1 | 分析者が、読む前に食い違いを知る | Want | 解決 | 高（人間、#297） | 課題1 |
| W2 | 分析者が止まる回数が増えない | Want | 費用 | 高（人間、Epic 35） | 課題1 |
| W3 | 同じ指摘が1か所にだけ出る | Want | 解決 | 中（Claude の推測） | 課題2 |

判断1 の案。

- 案1A: 見せて聞く。終え方の問いの冒頭に食い違いを並べ、分析設計ごとに、このまま読むか、計算し直させるかを聞く。
- 案1B: 自動で1回直させる。実行エージェントに分析設計どおりに計算し直させ、残った食い違いだけを見せる。
- 案1C: 分析ノートに出すだけで、問いは足さない。
- 何もしない（点検の結果を記録するだけ）。

判断2 の案。

- 案2A: 絞る。判定の線の写しと cell の並びは計算の点検へ移し、結果のレビューは、値と判定の矛盾、図、guardrail、解釈と交絡を見る。
- 案2B: 絞らない。Step 3b は今のままにする。

| Must | 案1A | 案1B | 案1C |
|---|---|---|---|
| M1 | 満たす | 満たさない恐れがある。分析設計どおりに計算できない理由があったとき、聞かずにデータへ触り直す | 満たす |

| Want | 案1A | 案1C |
|---|---|---|
| W1 | 問いの冒頭で知る | 分析ノートを開くまで知らない。開かずに答えることもできる |
| W2 | 増えない。既にある問いの冒頭に足す | 増えない |

| Want | 案2A | 案2B |
|---|---|---|
| W3 | 1か所に出る | 判定の線の写しと cell の並びが、点検とレビューの2か所に出る |

- 差がつく基準: 判断1 は W1、判断2 は W3。
- 感度: どの重みを動かしても変わらない。

| 案 | 起きうる悪い結果 | 抑え方 |
|---|---|---|
| 案1A | 小さな食い違いでも、毎回聞かれる | 食い違いが無い分析は、1行で済ませる。聞くのは食い違いがある分析だけである |
| 案1A | 終え方の問いが長くなる | 食い違いは、分析設計ごとの見出しの下の先頭に置く。項目と、何が違うかの文だけを出す |
| 案1B | 理由のある逸脱を、知らせずに消す | 無い |
| 案1C | 読んで答えた後に、食い違いに気づく | 無い |
| 案2A | 結果のレビューを受けない分析で、判定の線の写しを誰も見ない | 計算の点検が、判定の基準の項目として見る。点検は任意でない |
| 案2B | 分析者が、同じ指摘を2回読む | 無い |

## Decision

案1A と案2A を採る（人間の判断、2026-11-28）。決め手は、判断1 が W1、判断2 が W3 である。

1. 計算の点検に食い違いが無い分析は、読むものの所で、点検が済んだことを1行で言う。
2. 食い違いがある分析は、終え方を聞く問いの冒頭に、食い違いを並べる。項目と、何が違うかの文を出す。
   その分析について、このまま読むか、計算し直させるかを聞く。終え方の3つの問いはその後に同じ問いの中で続ける。
   分析者が止まる回数は増やさない。
3. このまま読むと答えた分析は、終え方の答えのとおりに進める。点検の記録は残り、分析ノートが食い違いを出し続ける。
4. 計算し直させると答えた分析は、食い違いを添えて実行し直す。まとめて任せた実行では実行エージェントに渡し直し、
   単独の経路では同じセッションが notebook を直して走らせる。抽出を変えないので、premortem はやり直さない。
   計算し直した分析は、もう一度点検してから終え方を聞く。
5. エージェントは食い違いを自動で直さない。
6. 結果のレビューは、値と判定の矛盾、図、guardrail、解釈と交絡（別の説明がつかないか、どこまで言えるか）を見る。
   判定の線の写しと cell の並びは、計算の点検が見る。
7. 結果のレビューを勧める目安は2つにする。判定で終わること（検証）と、数の照合がデータの中の足し上げだけであることである。
   「分析が設計に無いものを足したとき」は、計算の点検が拾うので、目安から外す。

## Consequences

### Positive

- 分析者は食い違いを知った上で分析ノートを読む。読んで答えたことが後から変わりにくい。
- 止まる回数は増えない。
- 結果のレビューが、計算の点検の見ないこと（解釈と交絡）に向く。

### Negative

- 食い違いがある分析では、終え方の問いが長くなる。分析設計が3つで、どれにも食い違いがあると、1つの問いに並ぶ文がかなり増える。
  読み切れるかは実データで使う段で確かめる。
- 「止める」は選べない。結果が記録にある分析は止められない（ADR-0064）。やり直したいときは、終え方で派生を選ぶ。
- 計算し直すと、前の実行が journal に書いた出来事が残る。答えがそれを引用しうる。この ADR では塞がない。
- 結果のレビューを受けたことのある分析設計は、古い観点のコメントを持つ。そのまま読める。

## Alternatives considered

- **食い違いがある分析を、終え方の問いから外して別に聞く** — 止まる回数が増える。Epic 35 が減らしたものを戻すことになる。
- **食い違いの重さをエージェントが判断し、軽いものは聞かない** — 重さの線に根拠が無い。分析者が読んだ内容に関わるかは、分析者が決める。
